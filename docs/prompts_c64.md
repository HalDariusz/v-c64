# PROMPT 1: KVM Hypervisor Skeleton in C (`kvm_host.c`)

**Prompt text:**

> Write a complete, minimalistic hypervisor in C (`kvm_host.c`) for Linux, using the `/dev/kvm` interface directly via `ioctl` (without QEMU or libvirt).
>
> The hypervisor must:
> 1. Initialize a virtual machine (`KVM_CREATE_VM`) and a vCPU (`KVM_CREATE_VCPU`).
> 2. Use `mmap` and `KVM_SET_USER_MEMORY_REGION` to map three physical guest memory regions:
>    - RAM (`0x00000 - 0x7FFFF`, 512 KB)
>    - VGA framebuffer (`0xA0000 - 0xBFFFF`, 128 KB)
>    - BIOS/reset vector (`0xF0000 - 0xFFFFF`, 64 KB)
> 3. Load the guest binary file `c64_guest.bin` at address `0x00000`.
> 4. Set up the x86 reset vector at address `0xFFFF0` with a `JMP FAR 0x0000:0x0000` instruction.
> 5. Run a `KVM_RUN` loop handling `KVM_EXIT_IO` exits (for the keyboard port `0x60` and the terminal output port `0x5001`) and `KVM_EXIT_HLT`.
> 6. Include GCC build instructions and a note about `/dev/kvm` permissions.

# PROMPT 2: Bare-Metal Boot and VESA Setup (`boot.s` and `linker_raw.ld`)

**Prompt text:**

> Write an x86 NASM boot assembly file (`boot.s`) and a linker script (`linker_raw.ld`) for a bare-metal system with no operating system.
>
> Requirements:
> 1. `boot.s` must include a Multiboot 1 header immediately requesting VESA VBE graphics mode at 640x480 resolution in an 8-bit palette (256 colors).
> 2. The code must initialize a 16 KB stack in the `.bss` section, pass a pointer to the Multiboot structure from register `ebx`, and call the C function `kernel_main(multiboot_info_t* mbi)`.
> 3. The linker script must lay out sections (`.text`, `.rodata`, `.data`, `.bss`) starting exactly at address `0x00000000`.
> 4. Provide the exact `nasm`, `gcc`, `ld`, and `objcopy -O binary` commands needed to produce a clean binary file with no ELF headers.

# PROMPT 3: 6510 Emulation Core, Memory Mapping and PLA Logic

**Prompt text:**

> Write a C kernel module (`memory_pla.c` and `memory_pla.h`) integrating a MOS 6502/6510 CPU emulator (e.g. `fake6502.c`) with an authentic Commodore 64 PLA memory-management layout.
>
> Requirements:
> 1. Implement support for the CPU register at address `$0001` (port direction register) and the `LORAM` (bit 0), `HIRAM` (bit 1), and `CHAREN` (bit 2) bits.
> 2. Implement the functions `read6502(uint16_t addr)` and `write6502(uint16_t addr, uint8_t val)`, switching visibility between 64 KB RAM, ROM chips (BASIC `$A000-$BFFF`, KERNAL `$E000-$FFFF`, CHARGEN `$D000-$DFFF`), and the I/O register area (`$D000-$DFFF`).
> 3. Include tables holding the ROM data as embedded C byte arrays generated by `xxd`.

# PROMPT 4: CIA 6526 I/O Chip Emulation (Timers and Keyboard Matrix)

**Prompt text:**

> Write a complete C emulation of the CIA 1 (`$DC00-$DCFF`) and CIA 2 (`$DD00-$DDFF`) chips for a bare-metal Commodore 64.
>
> Requirements:
> 1. CIA 1: Implement Timers A and B counting CPU cycles and generating periodic IRQ interrupts (50 Hz / 60 Hz for the C64 system clock and cursor refresh).
> 2. Keyboard: Implement the 8x8 keyboard matrix (reading Port A and Port B at `$DC00` and `$DC01`) and a function mapping PS/2 keyboard scancodes from x86 port `0x60` onto the corresponding C64 row/column intersections.
> 3. CIA 2: Implement the `$DD00` register controlling the 16 KB video memory bank selection for the VIC-II chip.

# PROMPT 5: Full VIC-II Graphics Engine (Rasterizer, Sprites, Framebuffer)

**Prompt text:**

> Write an efficient C emulator of the VIC-II graphics chip (`$D000-$D3FF`) for the Commodore 64, rendering into a 640x480 VESA memory buffer.
>
> Requirements:
> 1. Support the 16 original C64 colors (converted to an RGB/VESA palette).
> 2. Implement video modes: Standard Text Mode (40x25), Multicolor Text Mode, Standard Bitmap (320x200), and Multicolor Bitmap.
> 3. Implement 8 hardware sprites (Sprites 0-7) with X/Y coordinate support (including the 9th X-position bit in register `$D010`), double width/height (`$D01D`, `$D017`), and priority relative to the background.
> 4. Implement the raster line register (`$D011`/`$D012`) and Raster IRQ generation.
> 5. Implement a function scaling the generated 320x200 frame (or 384x272 with a border) and writing it directly to the physical `vesa_framebuffer` address.

# PROMPT 7: Cartridge Port and Simons' Basic Integration (16 KB ROM)

**Prompt text:**

> Write a cartridge-handling module for the Commodore 64 in our C emulator, with a particular focus on the Simons' Basic cartridge (16 KB).
>
> Requirements:
> 1. Implement support for the `EXROM` and `GAME` expansion port hardware lines in the PLA logic.
> 2. Once the cartridge flag is enabled, map the first 8 KB block of the Simons' Basic ROM at address `$8000-$9FFF`, and the second 8 KB block at address `$A000-$BFFF` (replacing the standard BASIC ROM).
> 3. Implement the cartridge's automatic cold-start procedure: read the autostart vector from the cartridge header at `$8000-$8003` and redirect the 6510 CPU's RESET vector (`$FFFC-$FFFD`) to the Simons' Basic start address.

# PROMPT 8: 128 KB RAM Expansion (Standard REU 1750)

**Prompt text:**

> Write a C emulation of the official Commodore REU 1750 memory expansion module (RAM Expansion Unit), mapped at address `$DF00-$DF1F`, extending our computer's RAM by an additional 128 KB / 512 KB.
>
> Requirements:
> 1. Allocate a 128 KB buffer for the additional Expansion RAM.
> 2. Implement the REU DMA controller registers: C64 source address, REU destination address, transfer length, and the command register (`$DF01`).
> 3. Support DMA operations: C64 -> REU (write to expansion memory), REU -> C64 (read from expansion memory), and Swap (exchanging memory blocks within a single cycle).

# PROMPT 9: Virtual 1541 Disk Drive and Fast Loading of `.D64` and `.PRG` Files

**Prompt text:**

> Write a fast-loading mechanism (Fast Loader / HLE Hook) for our C64 unikernel that allows instant loading of programs from `.PRG` files and `.D64` diskette images from the host's hard disk.
>
> Requirements:
> 1. Intercept the KERNAL vector routines at address `$F4A5` (`LOAD`) and `$F5DD` (`SAVE`).
> 2. On a `LOAD "name",8,1` command, the guest C code should halt the 6510 CPU, request the KVM hypervisor to transfer the file over dedicated KVM I/O ports, write the bytes directly into the appropriate guest RAM address, update the program end-of-memory pointers in the Zero Page (`$2D-$2E`), and return from the routine with a success flag.

**Prompt text:**
